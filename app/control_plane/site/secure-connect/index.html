Managed WireGuard

Secure Connect

Olopa's zero-trust access plane: the control plane authorizes every WireGuard peer and can restrict, quarantine, or terminate a session in response to risk — without touching gateway interface state directly.

Overview

Secure Connect splits into three independently-failing planes:

PlaneLocationResponsibility
Endpoint runtime agent/agent/src/secure_connect/ Enrolls, holds the session state machine, applies WireGuard config locally, and owns the kill switch
Orchestrator app/control_plane/control_server/secure_connect/ Issues sessions, allocates tunnel addresses, assigns gateways, and reacts to risk signals from correlated alerts
Gateway plane app/secure_connect_gateway/ Plain WireGuard hosts running a reconciler that mirrors the peer set the orchestrator authorizes
Note: Secure Connect is deliberately isolated from the sensor and ingest loops on the endpoint — a control-plane or network failure is reported through its own health snapshot and never stops telemetry collection.

Session states

The endpoint session state machine has increasing severity tiers. Higher tiers apply a more restrictive network policy.

TierStatesMeaning
0 disabled · idle · enrolling · connecting · healthy Normal lifecycle — full profile access once healthy
1 elevated · degraded Heightened monitoring; still connected under the assigned profile
2 restricted Traffic confined to the profile's safe_cidrs only
3 quarantined / terminated Session keys revoked; the device must re-enroll a fresh session
Note: Relaxation is one-way outside of a full reconnect — the endpoint only ever accepts an operator-confirmed elevated → healthy downgrade on a live session. Recovering a restricted or quarantined device means terminating that session and starting a new one under the relaxed profile.

Endpoint config

Set on the olopa agent process to enable its Secure Connect client alongside normal sensor/ingest operation.

Env varDefaultDescription
OLOPA_SC_ENABLED disabled Set truthy to start the Secure Connect client
OLOPA_SC_CONTROL_URL — Control-plane base URL; must be https:// (set OLOPA_SC_ALLOW_INSECURE_HTTP=1 only for local dev)
OLOPA_SC_ENROLLMENT_TOKEN — One-time token redeemed at /api/v1/secure-connect/enroll
OLOPA_SC_MTLS_IDENTITY_PEM — Client identity cert used to bind the enrollment (required unless OLOPA_SC_ALLOW_UNBOUND_ENROLLMENT=1, local dev only)
OLOPA_SC_INTERFACE olopa0 Local WireGuard interface name (max 15 chars)
OLOPA_SC_TENANT_ID / OLOPA_SC_HOST_ID falls back to OLOPA_INGEST_TENANT_ID / OLOPA_INGEST_HOST_ID Tenant and host identity used for enrollment and sessions
OLOPA_SC_HEARTBEAT_MS 15000 Session heartbeat interval (floor 1000ms)
OLOPA_SC_POLICY_TTL_SECS 300 How long a fetched policy/profile is cached before refresh
OLOPA_SC_KILL_SWITCH on Blocks non-tunnel egress whenever the session isn't healthy. Set to 0/false/off to disable — not recommended outside local dev
OLOPA_SC_MTU 1420 WireGuard interface MTU (576–9000) 
export OLOPA_SC_ENABLED=1
export OLOPA_SC_CONTROL_URL=https://control.example.com
export OLOPA_SC_ENROLLMENT_TOKEN=eyJhbGciOi...
export OLOPA_SC_MTLS_IDENTITY_PEM=/etc/olopa/identity.pem

Register a gateway

Gateways are plain WireGuard hosts — the control plane never touches their interface config, only peer entries. Register one with admin credentials before deploying the reconciler:

curl -sS -X POST "$CONTROL_URL/api/v1/secure-connect/gateways" \
  -H "authorization: Bearer $ADMIN_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "eu-west-1a",
        "region": "eu-west",
        "public_key": "'"$(wg show olopa-gw0 public-key)"'",
        "public_endpoint": "198.51.100.7:51820",
        "client_cidr": "10.90.0.0/16",
        "dns_servers": ["10.90.0.53"],
        "capacity": 5000
      }'
Tip: client_cidr is the pool the orchestrator allocates endpoint tunnel addresses from. The gateway keeps the first host address (10.90.0.1) for its own interface — provision that with wg-quick or cloud-init, the reconciler never sets it.

Gateway reconciler

Runs on the gateway host. Every tick it pulls the authorized peer set from the control plane, diffs it against wg show <iface> dump, applies the difference with wg set (removals first), and reports liveness with a heartbeat.

Env varDefaultMeaning
OLOPA_GW_CONTROL_URL—Control-plane base URL (https required)
OLOPA_GW_GATEWAY_ID—Gateway id returned by registration
OLOPA_GW_TENANT_ID—Tenant scope for the peer query
OLOPA_GW_API_TOKEN—Bearer token with the operator role
OLOPA_GW_INTERFACEolopa-gw0WireGuard interface to manage
OLOPA_GW_INTERVAL_SECS15Poll interval — also the bound on revocation latency
OLOPA_GW_DRY_RUN0Log the plan instead of applying it
 
# Install and run under systemd
install -D -m 0755 reconciler.py /opt/olopa/secure_connect_gateway/reconciler.py
install -D -m 0644 olopa-sc-gateway.service /etc/systemd/system/olopa-sc-gateway.service
systemctl enable --now olopa-sc-gateway

# Or one-shot, e.g. from a deploy pipeline
python3 reconciler.py --once --dry-run --verbose

Revocation model

Peer removal is the revocation path — when the control plane quarantines, terminates, or rekeys a session, the old public key disappears from the peer list and the reconciler drops it from the interface on its next poll. There is no separate revocation API to call.

FailureBehavior
Control plane unreachable from the gateway Fails open on the gateway. The current peer set stays exactly as it is — cutting access requires a successful poll that says the peer is gone, so a control-plane outage never blacks out a fleet
Control plane unreachable from the endpoint Fails closed on the endpoint via the kill switch (OLOPA_SC_KILL_SWITCH, on by default) — non-tunnel egress is blocked whenever the session isn't healthy
Gateway stops heartbeating After CONTROL_SC_GATEWAY_GRACE_SECS (default 120s) it drops out of rotation and the orchestrator migrates its live sessions to a healthy gateway
Note: Revocation latency is bounded by OLOPA_GW_INTERVAL_SECS. The endpoint's own kill switch engages within seconds of a control-plane command; the gateway poll interval governs how fast the server-side peer entry actually disappears — set it at or below your revocation SLO.

Risk-driven response

The orchestrator subscribes to the correlation engine's alert stream (OIL respond actions) and can move a session down the severity ladder automatically. Operators can also drive the same transitions directly:

# Quarantine every session held by a device
curl -sS -X POST "$SC/devices/$DEVICE_ID/quarantine" \
  -H "authorization: Bearer $OPERATOR_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"reason": "correlated alert: credential exfil chain"}'

# Restrict a single session to its profile's safe_cidrs
curl -sS -X POST "$SC/sessions/$SESSION_ID/state" \
  -H "authorization: Bearer $OPERATOR_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"desired_state": "restricted", "reason": "elevated risk score"}'
Note: Restricting a session requires the session's profile to define safe_cidrs — there's nothing to fall back to otherwise. Relaxing a restricted or quarantined session isn't accepted in place; terminate it and let the device reconnect.

Capacity notes

Measured with app/control_plane/tools/sc_loadtest.py against a single uvicorn worker on SQLite: session establishment collapses past roughly 8 concurrent starts (SQLite serializes writers and establishment holds the write lock across several statements). Enrollment and heartbeat traffic scale fine at every level tested.

Production: any deployment beyond a pilot must run PostgreSQL (DATABASE_URL=postgresql+psycopg://...) — the ORM layer is portable, only the SQLite-specific PRAGMAs in control_server/db.py are conditional on the URL. 
python app/control_plane/tools/sc_loadtest.py \
  --control-url "$CONTROL_URL" --dev-token "$CONTROL_DEV_TOKEN" \
  --devices 500 --concurrency 8 --duration 120

The load test exits non-zero when an SLO target is missed, so it can gate a release.
